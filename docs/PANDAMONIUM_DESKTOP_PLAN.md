# Pandamonium Desktop — plan (draft for owner sign-off, 19 Nov 2026)

Pandamonium Desktop replaces Minima Core Desktop. Reference: Pandamonium 2.2.52
(`apks/base`, branch `companion-chooser-2026-11-10`, commit `be7c8be407efc85000d19eac0846bbcbcb3398c5`).
Work happens in this worktree: `desktop/pandamonium-desktop`, branch `pandamonium-desktop`,
started from `origin/master` 0.18.64 (`def5e8e`).

Status: research done. Nothing built. Owner decisions D1–D7 below are open.

## 1. What the research found

- Every Minima Core Desktop tab except Parlons was redrawn by hand; none reuses its original's
  screens. The shell uses a desktop-only palette that matches no original.
- Chat, Mail and AtomiX styles already match their Pandamonium versions. The shell and Pools do not.
- Mail is 20 versions behind the Android app (desktop matches 0.5.8; Android is 0.5.28): no six-word
  addresses, no MxUSD payments, no full threads, no text selection.
- Three identifier or naming defects exist today and are fixed in phase 0: the ETH Wallet card and
  History rows shorten identifiers; Vestr shortens its contract address
  (`0x3C432D5099AB27EA901079EF54D9A97AB4DB3BD1CFFF670296C31B7C83C1C8BE`); miniMall says "mxUSDT".
- The app's data folder is named after `productName` ("minimaCore") and nothing pins it. A rename
  would orphan every user's swaps, pools, mail, chat and history.
- The desktop node jar has no block-as-key-uses mode. Pandamonium defaults to it. The same 24 words
  give different keys in the two modes.

## 2. The reference: what Pandamonium is

- Toolbar "Minima Core" / "Pandamonium"; footer with block height and key count.
- Tabs: Wallet · Dexicon · History · Apps · Chat · Node. Chat hides when Keets is off; Dexicon hides
  when switched off.
- Apps: a list of integrated apps, each with On/Off and freeze, drag to reorder, order saved.
- Overflow menu: Logs, Terminal, Backup, Startup Params, App lock, Shutdown, Reset, Language.
- Look: Manrope; orange `#FF4A2B`, blue `#2F6BF6`; dark `#0F1114` / light `#F4F5F7`, following the
  system; cards 16 radius, 1px outline, no shadow; controls 12; buttons sentence case; 8-unit grid.
- Each integrated app keeps its own design inside the shell: Mail is warm paper with orange
  `#F7931A`; Dexicon, AtomiX and Pools use Dexicon's night palette with Inter and JetBrains Mono.

## 4. Phases

Each phase is a run of small versions: one change, one version, one commit.

**Phase 0 — Safe foundations (no visible redesign yet)**
1. Pin the data folder to the existing `minimaCore` location before any rename. Test: upgrade keeps
   swaps, pools, mail, chat, history.
2. One signing queue for the whole process (DexiconPro's `main/noderun.js`); AtomiX and PandaPools go
   through it. This is the highest-risk change and lands before a third signer exists.
3. Fix the identifier and MxUSD defects listed in section 1.
4. Remove P2P Chance. A user with an open bet keeps the settle/reclaim path until it clears; keychain
   entries are never wiped.

**Phase 1 — The shell**
Pandamonium tokens, toolbar, tab bar, Apps list (On/Off, reorder), overflow menu, footer, system
light/dark. Existing tabs sit inside it unchanged at first.

**Phase 2 — Core screens**
Wallet, Receive, Send, History, Node, Settings / Startup Params / Backup, first run.

**Phase 3 — Dexicon**
Exchange hosted (public service: auto-cross on, no DexiconPro gates, user's relay list). Then ① and
② reproduced from the Android Dexicon screens over the existing engines. Old Pools and AtomiX tabs
are removed only after a parity audit of ① and ②.

**Phase 4 — Messaging**
Mail up to 0.5.28; Chat gaps (voice recording, files, retry); Parlons placement per D4.

**Phase 5 — Apps**
ETH Wallet, Vestr, Faucet, KeyUses, Terminal, Logs, Web Wallet, then the three new ones: Future Cash
Next, Explorer, Entropy.

**Phase 6 — Languages and release**
zh / ru / uk as in Pandamonium. Release on all three platforms through `scripts/release-desktop.sh`;
mac DMG signed and notarized.

## 5. Risks

| Risk | Guard |
|---|---|
| Data folder moves on rename | Pinned in phase 0, upgrade test before anything else |
| Three engines signing at once reuse a one-time key | One signing queue, phase 0 |
| Key mode switch cuts users off from live swaps and pools | Existing installs never change mode (D1) |
| Auto-cross trades against the user's own pool | Verify the guard before the Exchange ships |
| Open casino bet stranded | Settle path kept until clear |
| Local-only history lost (`mail.json`, `chat.json`, `shop.json`, `history.sqlite`) | Files untouched; no app is re-keyed |
| Future Cash Next covenant or transaction order altered | Hosted unchanged; service runs verbatim |
| ETH sends starve gas for swaps in flight | Keep the shared ETH send queue |

## 7. Block-as-key-uses on the desktop

Nothing in principle stops it. Two practical things do today:

1. The desktop's bundled node jar (sha256 `8cb690406b31d68ff218066c4986c67bfbf488d394fe25c879ace62501c42ea9`) is built
   from a line without the `-blockaskeyuses` flag. Pandamonium's jar (`apks/base/app/libs/minima.jar`, sha256
   `32f29846c07874dc530feda958b9fdbb4c0bbfabaadee463063b54d90ff2fdc9`) has block mode, low-RAM mode and keets, but it
   is the Android build: it does not bundle BouncyCastle or H2, so the desktop must supply them. Unproven on desktop.
2. The same 24 words give different keys in the two modes. An existing desktop wallet switched to block mode would
   lose sight of its funds and could no longer sign for its live swaps and pools.

So: new wallets can be block mode by default with a Classic mode switch, as in Pandamonium; existing wallets stay
classic unless the user deliberately moves (drain swaps, close pools, send funds to the new wallet).

### Future Cash Next: read, and not built (20 Nov 2026)

Read: `mds/futurecash-next` 3.2.1 (`e48c523420940bfbb703626d60a2971230bcb8b3`): `guardian.js` (the engine, loaded by the page AND, with `svc-main.js`, as `service.js`), `ui.js`, `index.html`; and Pandamonium's native copy (`apks/base` `integrated/futurecash-next`). The MiniDapp page has the phone's four tabs (Guardian, Stakes, Activity, Help), so hosting it would look right. It was not hosted, because it cannot be made safe in one pass:

1. **It must run with WRITE permission, and then it signs by itself.** The engine treats the node's "pending" answer as a failure ("Future Cash doesn't work in READ mode, switch it to WRITE in MiniHub"). With WRITE, a background service acts on every new block with nobody at the screen: it collects matured stakes (`txncreate` / `txninput` / `txnoutput` / `txnbasics;txnpost`, no signature: the contract pins the payout), and it SWEEPS coins from an at-risk address to a "safe address" with `txnsign publickey:<key>`. The safe address comes from the app's own key-value store (typed in the page, or a `newaddress`); the at-risk set comes from a remote audit service. The desktop's rule (a native confirmation before anything is signed, no weaker than the node's Pending list) and an engine built to sign unattended need a designed answer: a one-time native grant, plus a sign gate in the main process that checks each transaction with `txnlist` (a collect pays only the stake's own state-port-2 address; a sweep pays only the destination the user confirmed natively) as `main/dexicon-signgate.js` does for the Exchange page. That gate needs the node's real `txnlist` shapes, which cannot be seen here.
2. **It rewrites the wallet's script table.** `newscript trackall:true script:"RETURN SIGNEDBY(…)"` RETIRES a reused default address (the node then never gives change to it), and `newaddress` mints a key. Both change the one wallet that AtomiX, PandaPools, Dexicon and Send share (their change addresses, and a new key on a block-key wallet). Nothing in the desktop reviews that today.
3. **Unbounded reads on every block.** `coins relevant:true` (three places) and `scripts` are sent with no bound; the page and service must stay byte-identical, so the bound would have to be invented in the shim, and the node has no paged form of that read.
4. **Coin guard.** `main/reserve.js` would record the service's `txninput` coins under a new owner, and lets every contract coin through. But a collected coin waiting to be swept is an ordinary wallet coin on the payout address: the wallet's Send, Consolidate or another engine can spend it first (the sweep then fails and retries; with an at-risk key that is the race the app exists to win). A hold source for `fc_collect` / `fc_sweep` rows is needed, and an answer to chains (`txnbasics id:X;txnpost id:X` is one command to the guard).
5. **Store and service.** Two H2 tables (`fc_collect`, `fc_sweep`; upper-case column names, `CAST(… AS DOUBLE)`), 28 key-value keys shared by page and service, `MDS.notify`, NEWBLOCK / NEWBALANCE events with the block header. The H2-to-SQLite shim used by the three engines has never run these statements.
6. **Gates.** Freeze, the Quit warning and the restore gate must each read `COLLECT_POSTED`, `SWEEP_POSTED` and `PENDING` rows and fail closed; a wallet replacement must move the store aside (the keys in `clean_addr` and the sweep keys die with the old wallet).
7. **None of it can be run here.** A money engine that signs unattended, shipped on tests against stand-ins alone, is the unreviewed hole the brief forbids.

## 10. Proposed addition to the Parlons node (for the owner to approve; nothing in the maxima repo was changed)

Why: with the panel in the browser, the app learns of Parlons events only from two log lines that were written for people. They carry the sender's key instead of a name, the message's own text, and for calls they are printed only while a device is live. A call that arrives with the browser closed is declined silently.

The smallest change (about six lines of Java; neither 0.2.152 nor 0.2.153 has it), all in `account/src/main/java/com/eurobuddha/maxima/cloud/ParlonsControl.java`:

1. In `push(JSONObject, String)` (the one place every event passes), after the local sink: when `type` is `message` and it is not ours, print `[parlons-notify] {"type":"message","peer":"<key>","name":"<conversation name>"}`; when `type` is `call` and `kind` is `offer`, print `[parlons-notify] {"type":"call","from":"<key>","name":"<contact name>","ref":"<call id>"}`. No message text. Built with the node's own JSON writer, so a name cannot break the line.
2. In `forwardCallSignal`, in the branch that declines because no device is live: print `[parlons-notify] {"type":"missed-call","from":"<key>","name":"<contact name>","ref":"<call id>"}`.
3. Behind `-Dparlons.notify.stdout=true`, which this app would pass, so hosted nodes stay quiet.

That gives truthful message and call notices and "missed call". It does not make a call answerable from a notification. For that, two further changes would be needed, and they are a design decision rather than a small addition: keep the last offer of a call for 90 seconds and replay it to a tab that connects (`ParlonsLocal.events()` after `hello`; the panel already accepts offers up to 90 seconds old), and do not decline at once while the desktop app has said it is watching.

Not chosen: letting the app use the one-time ticket to open a panel session of its own and listen there. It would work on today's node for messages, but a listening session counts as a live device, so the node would stop declining calls that no tab can then answer, and each use rotates the ticket file.

## 11. Owed in other repos after the Phase 4 security review (0.19.4; nothing there was changed)

The app now believes only whole lines of the node's own shape, but a line is whatever the node printed, and both nodes print a peer's text unsanitised. Until they stop, a peer who embeds a line end and imitates the node's own ending can still make a whole line (see the 0.19.4 changelog for what that line can and cannot do).

1. maxima, `account/src/main/java/com/eurobuddha/maxima/cloud/ParlonsCore.java` `log(String)`: replace every control character (`\p{Cntrl}`, U+2028, U+2029) in the line with a space before `System.out.println`, so one `log()` call is always one physical line. `ParlonsControl.forwardCallSignal` prints `cm.state` and the contact's name as they came (`safe()` only turns null into ""); `ParlonsCore.shortPeer` prints `e.sender` as it came.
2. core (minima-core, and the same file in maxima's embedded node), `org/minima/system/network/minima/NIOMessage.java` about line 332: the greeting's version is logged verbatim in "Greeting with Incompatible Version!". Strip control characters and bound its length there (or in `MinimaLogger.log` for every line).
3. Until then (0.19.106): a peer's text carrying a line end AND an imitation of the node's own line ending can make a whole line the app cannot tell from the node's own. It can raise a notification; it cannot change a Parlons flag once the account is up, and it cannot stop the node after the node's first answered health poll. The boot-line and prefix rules stay when the nodes are fixed.
